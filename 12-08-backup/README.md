## Задание 1. Резервное копирование

**Кейс.** Финансовая компания решила увеличить надёжность работы баз данных и их
резервного копирования. Нужно описать подходящие варианты резервного копирования.

### 1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день

Подходит **полное (full) резервное копирование по расписанию — раз в сутки**.

Каждую ночь (в период минимальной нагрузки) снимается полная копия всей базы:

- **логический бэкап** — `pg_dump` / `mysqldump` (дамп в виде SQL), удобно для
  переносимости и восстановления отдельных объектов;
- либо **физический бэкап** — `pg_basebackup` / копия файлов данных / снапшот,
  быстрее восстанавливается на больших объёмах.

Так как требуется восстановить состояние «за предыдущий день» целиком, достаточно
одной полной копии за сутки. Хранить копии по принципу ротации (например,
последние 7 ежедневных + 4 еженедельных). Для регулярного снятия бэкапа со slave,
чтобы не нагружать боевой master.

### 1.2. Необходимо восстанавливать данные за час до предполагаемой поломки

Одного суточного бэкапа мало — нужна возможность восстановиться на **произвольный
момент времени**. Это **Point-in-Time Recovery (PITR)**:

- **полный бэкап (базовый) + непрерывное архивирование журналов транзакций**:
  - PostgreSQL — базовая копия `pg_basebackup` + архивирование **WAL**
    (`archive_command`, `restore_command`, `recovery_target_time`);
  - MySQL — полный бэкап + **бинарные логи (binary log)**, накат
    через `mysqlbinlog` до нужной отметки времени (`--stop-datetime`).

Механизм: берём последнюю полную копию и «накатываем» на неё журналы транзакций
до нужного момента (например, до `2026-07-23 14:00:00` — за час до поломки).
Дополнительно между полными копиями можно снимать **инкрементальные** бэкапы,
чтобы уменьшить объём наката журналов и ускорить восстановление.

### 1.3.* Возможен ли моментальный переход на работающую/починенную базу

Да, это реализуется **репликацией + автоматическим переключением (failover)** и
называется **High Availability (HA)**. Резервная база держится в актуальном
состоянии (горячий резерв, hot standby) и при поломке master нагрузка мгновенно
(секунды) переводится на неё:

- **PostgreSQL** — потоковая репликация (streaming replication) + автопереключение
  через **Patroni**, repmgr, pg_auto_failover; общий виртуальный IP.
- **MySQL** — **InnoDB Cluster / Group Replication**, MHA, Orchestrator +
  ProxySQL / балансировщик.
- Приёмы: виртуальный IP (VIP) + keepalived, прокси, который сам направляет
  трафик на живой узел.

Ключевое отличие от бэкапа: бэкап защищает от потери данных, а репликация с
failover обеспечивает **непрерывность обслуживания** (минимальные RTO/RPO). На
практике используют оба подхода вместе.

## Задание 2. PostgreSQL

### 2.1. Пример команды резервирования и восстановления (pg_dump / pg_restore)

По официальной документации PostgreSQL
(<https://www.postgresql.org/docs/current/app-pgdump.html>,
<https://www.postgresql.org/docs/current/app-pgrestore.html>).

**Резервное копирование** базы `mydb` в custom-формате (сжатый, для `pg_restore`):

```bash
pg_dump -U postgres -F c -f mydb.dump mydb
```

где `-F c` — custom-формат, `-f` — файл вывода.

**Восстановление** из custom-формата с пересозданием базы:

```bash
# создать пустую базу и восстановить в неё
createdb -U postgres mydb_restored
pg_restore -U postgres -d mydb_restored mydb.dump

# либо с автоматическим пересозданием базы (-C создаёт БД, -d указывает на служебную)
pg_restore -U postgres -C -d postgres mydb.dump
```

Альтернатива — обычный SQL-дамп (plain text) и восстановление через `psql`:

```bash
pg_dump -U postgres mydb > mydb.sql        # бэкап
psql   -U postgres -d mydb -f mydb.sql     # восстановление
```

### 2.1.* Возможно ли автоматизировать этот процесс? Если да, то как

Да, автоматизировать можно и нужно. Основные способы:

1. **cron / systemd timer** — самый простой вариант. Скрипт с `pg_dump` по
   расписанию, с датой в имени файла и ротацией старых копий:

   ```bash
   # /etc/cron.d/pg_backup — каждый день в 02:00
   0 2 * * * postgres pg_dump -F c mydb -f /backup/mydb_$(date +\%F).dump \
       && find /backup -name 'mydb_*.dump' -mtime +7 -delete
   ```

2. **Непрерывное архивирование WAL + PITR** — для восстановления на любой момент:
   в `postgresql.conf` включается `archive_mode = on` и задаётся `archive_command`,
   которая копирует WAL-сегменты в архив/хранилище.

3. **Специализированные инструменты** — `pgBackRest`, `Barman`, `WAL-G`. Они
   умеют полные + инкрементальные бэкапы, дедупликацию, сжатие, отправку в S3,
   расписание и проверку целостности «из коробки».

4. **Снятие бэкапа со slave-реплики**, чтобы не нагружать боевой сервер.

## Задание 3. MySQL

### 3.1. Пример команды инкрементного резервного копирования базы данных MySQL

**Вариант A. MySQL Enterprise Backup (`mysqlbackup`)** — «родной» инкрементальный
бэкап по документации
(<https://dev.mysql.com/doc/mysql-enterprise-backup/en/mysqlbackup.incremental.html>).

Сначала — полный (базовый) бэкап:

```bash
mysqlbackup --user=root --password \
  --backup-dir=/backup/full \
  backup-and-apply-log
```

Затем — **инкрементальный** бэкап (только изменения с момента предыдущего бэкапа):

```bash
mysqlbackup --user=root --password \
  --incremental \
  --incremental-base=dir:/backup/full \
  --incremental-backup-dir=/backup/inc1 \
  backup
```

Ключевые опции: `--incremental` включает инкрементальный режим,
`--incremental-base=dir:...` указывает на предыдущий бэкап (база для вычисления
изменений), `--incremental-backup-dir` — куда класть инкремент. Альтернативно
базу можно задать через `--incremental-base=history:last_backup` (по данным из
таблицы истории бэкапов).

**Вариант B. Инкремент на основе бинарных логов (binary log) — штатная MySQL
Community.** По документации это называется Point-in-Time (Incremental) Recovery
(<https://dev.mysql.com/doc/refman/8.0/en/point-in-time-recovery.html>).

Полный бэкап с ротацией бинлога:

```bash
mysqldump --single-transaction --flush-logs --master-data=2 \
  --all-databases > /backup/full.sql
```

`--flush-logs` закрывает текущий бинарный лог и начинает новый — с этого момента
все изменения пишутся в свежий бинлог, который и будет «инкрементом».

Снятие инкремента = сохранение накопившихся бинарных логов. Принудительно закрыть
текущий бинлог и забрать готовые:

```bash
mysqladmin flush-logs
# бинлоги накопленных изменений (пример имён)
cp /var/lib/mysql/binlog.000002 /var/lib/mysql/binlog.000003 /backup/incremental/
```

Восстановление = полный дамп + накат бинлогов (в т.ч. до нужного момента времени):

```bash
mysql < /backup/full.sql
mysqlbinlog /backup/incremental/binlog.000002 /backup/incremental/binlog.000003 \
  | mysql
# либо PITR до конкретной отметки времени:
mysqlbinlog --stop-datetime="2026-07-23 14:00:00" binlog.000003 | mysql
```
